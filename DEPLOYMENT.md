# Production deployment checklist

Everything the app needs to run somewhere other than your laptop.

---

## 1. You are already on MongoDB Atlas

Worth stating plainly, because it is a common mix-up: **MongoDB Compass is not a
database.** It is a desktop GUI for browsing a MongoDB server. When you open
Compass and see your collections, you are looking at your Atlas cluster in the
cloud — nothing is stored on your machine.

Your `DB_URL` is:

```
mongodb+srv://sanskaradmin:********@meripanchyatcluster.88q9wor.mongodb.net/
```

`mongodb+srv://…mongodb.net` is an Atlas SRV connection string. There is no
local database and nothing to migrate.

---

## 2. Prepare the cluster for production

### 2a. Rotate the database password

The current password has been shared in plain text (it also contains `@`, which
has to be percent-encoded as `%40` in the URL — a recurring source of confusing
auth errors). Before going live:

1. Atlas → **Database Access** → edit the `sanskaradmin` user → **Edit Password**
   → *Autogenerate Secure Password* → **Update User**.
2. Copy the new password and update `DB_URL` in `.env.local` **and** in your
   hosting platform's environment variables.
3. If the password contains `@ : / ? # [ ] %`, percent-encode it.

Better still, create a **second** database user for production only, so a leaked
dev credential cannot touch live village data.

### 2b. Open Network Access

By default Atlas only accepts connections from IP addresses you have listed.
Your laptop's IP is probably the only entry, so a deployed server will hang and
then fail with `serverSelectionTimeoutMS` after 10 seconds.

Atlas → **Network Access** → **Add IP Address**:

- **Vercel, Netlify, Render free tiers** — these do not publish fixed outbound
  IPs, so you must allow `0.0.0.0/0` (anywhere). This is normal for serverless
  hosting; your database is still protected by username and password. Use a
  strong autogenerated password if you do this.
- **A VPS or a host with a static IP** — add just that IP. Much safer.

### 2c. Separate production data from test data

`DB_NAME` now selects which database inside the cluster is used
([app/utils/connection.js](app/utils/connection.js)). It defaults to
`meripanchayat`, so nothing changes unless you set it.

| Environment | `DB_NAME` |
|---|---|
| Local development | `meripanchayat` |
| Production | `panchayatx_prod` |

Set `DB_NAME=panchayatx_prod` on the host and production starts with empty
collections. Seed the first admin against it with:

```bash
DB_NAME=panchayatx_prod node scripts/seed-system-head.cjs <email> <password> "System Head"
```

To copy existing data across instead of starting fresh, use Atlas's built-in
tooling (`mongodump` / `mongorestore --nsFrom 'meripanchayat.*' --nsTo 'panchayatx_prod.*'`).

## 3. Environment variables on the host

**`.env.local` is git-ignored and is never uploaded.** Every variable must be
entered again in your hosting platform's dashboard (Vercel: Settings →
Environment Variables). Missing ones surface as a clear
`Missing required environment variable "X"` error thanks to
[app/utils/env.js](app/utils/env.js).

| Variable | Production value |
|---|---|
| `DB_URL` | Atlas string with the **rotated** password |
| `DB_NAME` | `panchayatx_prod` |
| `SESSION_SECRET` | A **new** random value — not the dev one |
| `NEXT_PUBLIC_URL` | Your real domain, e.g. `https://panchayatx.in` |
| `EMAIL_USER` / `EMAIL_PASS` | Gmail account + app password for OTP mail |
| `EDGE_STORE_ACCESS_KEY` / `EDGE_STORE_SECRET_KEY` | From your EdgeStore project |

Generate a production session secret:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"
```

Changing `SESSION_SECRET` invalidates every existing cookie, i.e. it logs
everyone out. That is also how you force a global logout if a secret leaks.

## 4. Where images and videos are stored

Not in MongoDB. The browser uploads the file to **EdgeStore**
(`files.edgestore.dev`), gets back a public URL, and only that URL string is
saved in Mongo.

| Bucket | Used by | Limits | Requires login |
|---|---|---|---|
| `publicFiles` | Community post media, work photos, documents | 50 MB, image/video/PDF | **Yes** |
| `profileImages` | Profile photos (signup + edit profile) | 5 MB, images only | No — see below |

Uploads used to be completely unrestricted: any visitor could POST to
`/api/edgestore` and store unlimited files of any type in your bucket. They are
now gated in
[app/api/edgestore/[...edgestore]/route.js](app/api/edgestore/%5B...edgestore%5D/route.js)
on a signed httpOnly session cookie, which the browser cannot forge.

Three things still to be aware of:

1. **`profileImages` accepts anonymous uploads.** It has to — signup lets you
   pick a photo before the account exists. It is capped at 5 MB and images
   only. To close it fully, move the photo step to *after* account creation.
2. **Deleting a post does not delete its files.** The URL is removed from
   Mongo, the file stays in EdgeStore forever. Storage only grows. Worth a
   cleanup job before video use becomes heavy.
3. **EdgeStore's free tier is ~1 GB.** Village meeting videos will consume that
   quickly. Check your quota before launch and consider Cloudinary or S3 if
   video becomes a main feature.

Profile photos previously went to a **Cloudinary** account instead, with the
cloud name and unsigned upload preset hardcoded in client-side JavaScript
([app/edit/page.jsx](app/edit/page.jsx)) — a second storage account with a
completely open upload endpoint. That now uses `profileImages` like everything
else. Old Cloudinary URLs already saved in the database keep working, so no
migration is needed, but that Cloudinary account can be closed once you are
happy.

## 5. Known gap: authentication

Sessions currently only guard **file uploads**. Every other API route still
trusts an email string sent by the browser, and
[app/api/user/login/route.js](app/api/user/login/route.js) compares passwords in
plain text.

The practical consequence: anyone who knows the admin's email address can call
`/api/community?viewer=<admin-email>` and read every commenter's phone number.

Before real villagers use this, the login route should verify the session cookie
rather than a posted email, and passwords should be hashed with `bcrypt`
(already a dependency). The signing helpers in
[app/utils/session.js](app/utils/session.js) are the building block for that.

## 6. After deploying

- [ ] Site loads on the real domain
- [ ] Login works and sets a `px_session` cookie (DevTools → Application → Cookies)
- [ ] Signup sends an OTP email
- [ ] Logged-in admin can publish a post with a photo
- [ ] Logged-out visitor **cannot** upload (that is the gate working)
- [ ] Community feed loads — confirms Atlas Network Access is correct
- [ ] `DB_NAME` points at the production database, not `meripanchayat`
